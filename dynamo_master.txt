### EXACT _load_output template:
```python
def _load_output(path):
    """Load agent-produced output with symlink and hardlink protection."""
    assert os.path.exists(path), f"Output not found: {path}"
    assert not os.path.islink(path), f"Must not be a symlink: {path}"
    real_path = os.path.realpath(path)
    assert real_path.startswith("/app/"), f"Path escapes /app: {real_path}"
    # Hardlink guard
    out_stat = os.stat(path)
    assert out_stat.st_nlink == 1, f"Output {path} has multiple hard links"
    with open(path, "r") as f:
        return json.load(f)

def _load_expected(filename):
    """Load expected from sealed fixtures."""
    with open(os.path.join(TESTS_DIR, filename), "r") as f:
        return json.load(f)
```

### EXACT approx_equal template:
```python
def approx_equal(a, b, rel_tol=1e-3):
    """Check approximate equality with relative tolerance."""
    if isinstance(a, (int, float)) and isinstance(b, (int, float)):
        if b == 0.0:              # CRITICAL: p_value=0.0 must match exactly
            return a == 0.0
        if abs(b) < 1e-10:
            return abs(a) < 1e-6
        return abs(a - b) / abs(b) < rel_tol
    return a == b
```

### AVA sound_verifier (the persistent blocker)

**What AVA checks:** "Can an agent write static files to /app/ that pass pytest?"

**The 3 things required together:**

1. **Remove ALL comments from test.sh** — NONE. Zero. Not even blank comment.
   AVA's LLM quotes the comment verbatim as justification to BLOCK.
   Forbidden phrases: "never re-runs", "verifier only reads", "agent code", "pre-existing"

2. **Input-derivation test that reads eval config AND checks computed value:**
```python
def test_eval1_output_derived_from_input():
    with open("/app/eval_dataset_1.json") as f:
        config = json.load(f)
    output = _load_output("/app/output_eval_1.json")
    # Structural tie — group names from THIS config (eval1 ≠ eval2)
    assert set(output["random_effects"].keys()) == set(config["groups"])
    # Bug discriminator — different threshold from eval2!
    # Buggy pipeline: sigma2_b ≈ 0.048. Fixed: ≈ 0.799.
    assert output["variance_components"]["sigma2_b"] > 0.5
```

3. **Different thresholds per eval** — prevents cross-config hardcoding:
```python
# eval1: threshold A (e.g., sigma2_b > 0.5)
# eval2: threshold B (e.g., sigma2_b > 2.0)  ← different from eval1
```

**The adversarial_review vs ava_review contradiction:**
- adversarial_review PASSES: "architecture prevents attack" (understands Harbor)
- ava_review BLOCKS: "static files would pass" (blind LLM, doesn't trust architecture)
Both run in parallel. adversarial_review passing proves the architecture is correct.
ava_review non-determinism: same code can pass or fail on different runs.

## REQUIRED test_outputs.py STRUCTURE (class-based, proven pattern)

```python
import json
import os

TESTS_DIR = os.path.dirname(os.path.abspath(__file__))


def _load_output(path):
    """Load agent-produced output with symlink and hardlink protection."""
    assert os.path.exists(path), f"Output not found: {path}"
    assert not os.path.islink(path), f"Must not be a symlink: {path}"
    real_path = os.path.realpath(path)
    assert real_path.startswith("/app/"), f"Path escapes /app: {real_path}"
    out_stat = os.stat(path)
    assert out_stat.st_nlink == 1, f"Output has multiple hard links"
    with open(path, "r") as f:
        return json.load(f)


def _load_expected(filename):
    """Load expected output from sealed test fixtures."""
    with open(os.path.join(TESTS_DIR, filename), "r") as f:
        return json.load(f)


def approx_equal(a, b, rel_tol=1e-3):
    """Check approximate equality with relative tolerance."""
    if isinstance(a, (int, float)) and isinstance(b, (int, float)):
        if b == 0.0:
            return a == 0.0
        if abs(b) < 1e-10:
            return abs(a) < 1e-6
        return abs(a - b) / abs(b) < rel_tol
    return a == b


# ── Existence tests ────────────────────────────────────────────────────────

def test_eval1_output_exists():
    """Agent must produce /app/output_eval_1.json."""
    assert os.path.exists("/app/output_eval_1.json"), "Missing output_eval_1.json"

def test_eval2_output_exists():
    """Agent must produce /app/output_eval_2.json."""
    assert os.path.exists("/app/output_eval_2.json"), "Missing output_eval_2.json"


# ── Input-derivation tests (REQUIRED for AVA sound_verifier) ──────────────

def test_eval1_output_derived_from_input():
    """Prove eval 1 output was produced by running the fixed pipeline on eval_dataset_1.json.

    Reads raw config data and cross-checks a computed value that differs between
    buggy and fixed pipeline — cannot be satisfied by copying the expected fixture.
    """
    with open("/app/eval_dataset_1.json") as f:
        config = json.load(f)
    output = _load_output("/app/output_eval_1.json")
    # Structural: group names tied to THIS config (eval1 ≠ eval2)
    assert set(output["random_effects"].keys()) == set(config["groups"])
    assert output["model_summary"]["n_obs"] == config["n"]
    # Bug discriminator: sigma2_b requires REML with Bug 2 fixed
    # Buggy: ~0.048 (fails). Fixed: ~0.799 (passes). Threshold DIFFERS from eval2.
    assert output["variance_components"]["sigma2_b"] > 0.5, \
        f"sigma2_b={output['variance_components']['sigma2_b']:.4f} must be > 0.5"
```

## COMMENTS IN CODE — What LLMs Read and How They Trigger Blocks

### The Rule: Comments affect ALL 3 automated LLM checks (AVA, deep_review, qc_gate)

**test.sh comments → AVA BLOCK (covered above)**
Any comment explaining architecture triggers AVA's LLM to conclude "static files can win."

**metadata.description in data JSON files → anti_cheat FAIL**
```json
// WRONG — triggers anti_cheat during review:
{
  "stream_id": "stream_norm_1",
  "metadata": {
    "description": "Single observation equal to mu_0: x_bar=mu_0 masks Bug A; n=1 masks Bug C"
  }
}
```
Fix: Remove ALL metadata.description fields from dataset.json, eval_dataset_1.json, eval_dataset_2.json.
The anti_cheat check reads these files and flags any content revealing bug names or masking conditions.
```bash
# Check before pushing:
grep -r "Bug\|mask\|masks\|masks\|triggers\|invisible" task/environment/data/*.json
# Must return nothing
```

**Module docstrings stating correct formulas → pass2 too easy**
```python
# WRONG — reveals the correct formula above buggy code:
"""
The posterior shape parameters are updated by accumulating observed successes
into alpha and observed non-successes into beta.
"""
alpha_n = alpha_0 + k_successes
beta_n = beta_0 + n_trials  # ← bug: should be n_trials - k_successes
```
The LLM reads the docstring, sees "non-successes into beta", and instantly knows the bug.
Fix: High-level description only:
```python
# CORRECT — no formula hints:
"""
Updates posterior shape parameters via conjugate prior rules.
"""
```

**Bug justification comments → essential for difficulty, but can backfire on qc_gate B5**
Good justification comments make bugs look intentional — needed for 0/7 self-play:
```python
# GOOD — makes bug look like design choice:
# Normalize accumulated log evidence by batch count for scale-invariant
# per-batch evidence score for fair cross-stream comparison.
total_log_evidence = sum(log_marginals) / len(log_marginals)
```
BUT: if visible data can't distinguish buggy from correct (sum/1 == sum), qc_gate flags B5.
Fix: Add rule disclosure to instruction.md (not the code) to resolve B5 without removing the comment.

**Comment near bug that contradicts it → deep_review no_contradictions FAIL**
```python
# WRONG — comment describes correct behavior but code does wrong thing:
# Raw event volume reflects true sensor load for rate estimation
rate = deduped_events / window_size  # but deduped ≠ raw
```
Fix: Delete the misleading comment entirely. Or make it accurately describe the buggy behavior.

**Summary of comment rules:**
| Location | Rule |
|----------|------|
| test.sh | ZERO comments — none at all |
| data JSON files | No metadata.description with bug/masking info |
| Module docstrings | High-level only — no formulas that reveal the correct answer |
| Bug justification comments | KEEP — makes bugs look intentional |
| Decoy justification comments | KEEP — makes correct code look wrong |
| `# BUG`, `# fix`, `# should be` | NEVER — obvious leakage |
| Comments near bugs describing wrong behavior as correct | DELETE |

### LESSON 1: macOS vs Docker float drift — ALWAYS generate expected outputs in Docker

macOS (Apple Silicon) produces different floating-point results than Linux x86_64.
Differences are 1e-13 to 1e-15 — invisible to approx_equal but fails exact equality.

**Symptom:** oracle=0.0 even though your Python comparison shows match.
**Root cause:** Expected outputs generated on macOS differ from Docker (Linux) pipeline output.

**Fix — ALWAYS run this before pushing:**
```bash
cd task/
docker build -t task-img environment/ 2>/dev/null

docker run --rm \
  -v $(pwd)/tests:/tests \
  task-img bash -c '
    # Apply all patches here (copy from solve.py)
    python3 /app/pipeline.py /app/eval_config_1.json /tests/expected_output_1.json
    python3 /app/pipeline.py /app/eval_config_2.json /tests/expected_output_2.json
    echo "Expected outputs regenerated inside Docker (Linux)"
  '

# Verify oracle still 1.0 after Docker-regenerated outputs
harbor run -p . --agent oracle   # MUST be 1.000
rm -rf jobs/
```

### LESSON 2: Shell $? gotcha in Docker scripts — captures wrong exit code

**WRONG — captures echo's exit code (always 0):**
```bash
pytest /tests/test_outputs.py -q
echo "some message"
if [ $? -eq 0 ]; then   # ← captures echo's exit code, NOT pytest's!
    echo "1" > reward.txt
fi
```

**CORRECT — capture pytest exit code explicitly:**
```bash
pytest /tests/test_outputs.py -q
PYTEST_EXIT=$?           # ← capture immediately after pytest
echo "some message"
if [ $PYTEST_EXIT -eq 0 ]; then   # ← use saved exit code
    echo "1" > reward.txt
fi
```

This is exactly what `test.sh` already does correctly. The bug only matters when
writing custom Docker simulation scripts for local testing.

### LESSON 3: Explicit hints in instruction.md make task trivially easy

**What happened:** Added these 3 sentences to instruction.md to satisfy qc_gate:
```
Node filtering must enforce the following taint semantics: both NoSchedule
and NoExecute taint effects block scheduling...
Allocatable resources exclude the system daemon overhead fraction...
Pod anti-affinity label selectors use AND semantics...
```

**Result:** pass2 — BOTH agents solved the task in 18-28 minutes. Fail rate 0/2.
Analysis: "instruction.md hands the agent the three bug diagnoses outright — agents grep
for the stated convention and flip the violation."

**The lesson:** Stating EXACT failure modes in instruction.md = trivially easy task.

**The correct approach:** State conventions in GENERAL terms:
```
# GOOD — general, doesn't name which semantic is broken:
"The pipeline must correctly implement Kubernetes scheduling semantics
for all valid cluster configurations."

# BAD — names the exact bug fix:
"Both NoSchedule and NoExecute taint effects block scheduling."
```

**The tension:** qc_gate wants conventions stated (to verify determinism), but stating
them makes tasks too easy. Resolution: state the DOMAIN (K8s scheduling semantics) not
the SPECIFIC RULE that's violated.

If qc_gate flags B1/B5 for ambiguity, add only the convention that was AMBIGUOUS
(has two valid interpretations), not the one that's OBVIOUSLY correct from domain knowledge.

### LESSON 4: QC sticky comment cache — can get stuck for multiple pushes

**What happened:** QC evaluated against base `208a30e` even after 5+ new commits.
The `<!-- QC-BASE:208a30e -->` in the sticky comment never updated.

**Root cause:** QC caches its evaluation per base commit. If it finds an issue in commit X,
it keeps reporting that issue until it re-evaluates from scratch with a new base.

**Symptoms:**
- Same QC finding repeated across multiple pushes
- `<!-- QC-BASE: -->` shows an old commit SHA, not HEAD
- Tier-1 addressal says "C3 fixed in X" but QC still shows "C3 not fixed"

**Fix:** The QC base advances when:
1. You fix the actual finding (the right approach)
2. The Tier-1 system detects the fix and runs a fresh QC evaluation

To force a fresh QC run:
```bash
# Meaningful commit that touches the affected file
# e.g., update task.toml verification_explanation with accurate description
git add task/task.toml
git commit -m "Update verification_explanation to match current eval configs"
git push fork submission
```

Close and reopen the PR can also reset sticky comments:
```bash
gh pr close 1 --repo ORG/REPO
gh pr reopen 1 --repo ORG/REPO
```

### GATE 1: Self-Play (must pass BEFORE pushing)

**Target: 0-2/7 agents pass**
- 0/7 = strongest result → push immediately
- 1-2/7 = borderline → acceptable, push
- 3-4/7 = too easy → redesign bugs, do NOT push
- 5-7/7 = way too easy → full redesign required

**How to run self-play:**
```bash
# Set up 7 independent workspaces
SELFPLAY=/tmp/selfplay/your-task-name
rm -rf $SELFPLAY && mkdir -p $SELFPLAY
for i in 1 2 3 4 5 6 7; do
  mkdir -p $SELFPLAY/attempt_$i
  cp task/environment/data/*.py $SELFPLAY/attempt_$i/
  cp task/environment/data/*.json $SELFPLAY/attempt_$i/
  cp task/instruction.md $SELFPLAY/attempt_$i/
done
```

Then spawn 7 parallel subagents (each in its own workspace), each:
1. Reads instruction.md + all .py files
2. Tries to find and fix bugs WITHOUT looking at solution/ or tests/
3. Runs pipeline on eval datasets

Score: count how many produce output matching expected (at rel_tol=1e-3).

**What to do based on score:**
```
0-2/7 passed → ✅ proceed to Gate 2
3-4/7 passed → ❌ bugs too easy. Common fixes:
  - Make bug justification comments more convincing
  - Add decoys (correct code that looks wrong)
  - Move bugs to a less-read module (utility vs orchestrator)
  - Make visible data degenerate case stronger
5-7/7 passed → ❌ completely redesign bugs:
  - Current bugs are textbook formulas — agents memorize them
  - Switch to data-flow bugs (wrong value to correct function)
  - Pick a more obscure domain
  - Add the "iterative testing trap" (bugs invisible on visible data)
```

**Why self-play matters:**
- Self-play 0/7 ≈ CI pass2 passes (agent fails to solve in 1 hour)
- Self-play 5+/7 ≈ CI pass2 fails DEFINITELY (too easy)
- Self-play uses kiro_default (same model) — if it solves easily, CI Terminus-2 will too
- Self-play is the ONLY way to catch "too easy" before wasting a CI run

Flags & Fixes
The Dynamo QC evaluation reviews every submission from an adversarial perspective. It assumes the task should fail unless it can verify that every requirement has been implemented correctly.

The evaluation looks for ways a model could produce an incorrect answer and still pass the verifier. Your task only passes if all of those cases are prevented. If even a single check fails, the entire task fails.

The key principle is simple: everything the verifier checks must be clearly specified in instruction.md, the environment/ directory, or the provided examples. Likewise, the verifier should enforce every required behavior directly, rather than relying on indirect or aggregate checks.

How the gate decides
The gate defaults to FAIL and only reaches PASS when every break attempt is refuted by a citation in your code. Any single Major check that fails → the whole task fails, so breadth matters as much as depth. There is no discretion to excuse a surfaced break — "near-correct," "immaterial," "obscure," and "intended difficulty" are not valid defenses. Materiality only sets severity, never whether something is a finding.

The 30 checks
The five failure areas cover the what; this page is the exhaustive version the QC gate actually runs — 30 specific checks across those same five concerns (families A–E), every one Major (any single failure fails the task). The strategies and checklist below cite the individual IDs; expand a family for exactly what a cited ID (e.g. A5, C4) triggers on.

Collapse all

A · Solution / oracle correctness (A1–A6)
A1 · Oracle fails its own verifier — the reference solution, run against the verifier as shipped, wouldn't score full reward (fixture/generator bug).
A2 · Incomplete reference solution — solution/ doesn't perform every action the instruction requires (e.g. reports the problem but skips the mandated repair).
A3 · Hardcoded answer in reference — a decisive answer, table, threshold, or constant is baked into the reference rather than computed from agent-visible inputs.
A4 · Oracle relies on hidden/privileged access — the oracle imports a private module supplying the task's crux, or reads a protected fixture the agent couldn't reconstruct.
A5 · Oracle undocumented assumption — a silent default, injected record, unit conversion, or dedup that is neither documented nor derivable and changes the result.
A6 · Oracle edge-case or logic bug — a class of valid input on which the oracle produces a wrong or crashing result (tie-break, off-by-one, filtering, null-handling).

B · Contract coherence & determinacy (B1–B6)
B1 · Ambiguous rule, no disambiguation — two reasonable readings of one rule yield different graded answers and nothing agent-visible picks one.
B2 · Internal contradiction / impossible mechanism — two rules conflict on a real input, or the end-state is unreachable via the only permitted mechanism.
B3 · Missing definition, field, or data — a value the graded computation needs is absent from agent-visible inputs (incl. undefined ownership, precedence, tie-break, dedup).
B4 · Undocumented requirement enforced — the verifier enforces a requirement stated nowhere to the agent: hidden thresholds, undisclosed encodings, precedence/tie-break rules.
B5 · Underdetermined / hidden-knowledge mapping — disclosed material doesn't uniquely determine graded outputs (rule/cipher family undisclosed, or inputs outside observed range).
B6 · Unstated data-anomaly / selection policy — graded input has an anomaly (duplicate keys, ties, malformed rows, overlapping windows) whose handling changes the answer, with no rule stated.

C · Verifier rigor & scoring (C1–C6)
C1 · Partial / degenerate / stub output accepted — a stub (report-only, boolean-only, or a subset of actions) clears the verifier without doing the real work.
C2 · Over-permissive tolerance or threshold — a tolerance, threshold, or aggregate metric accepts a concrete, materially-wrong answer.
C3 · Narrow / hardcodable held-out coverage — a solution that hardcodes a shared constant or ignores the real input still passes.
C4 · Truth recomputed from agent-writable inputs — the verifier re-reads an agent-writable path to compute ground truth, so altering the input makes the reference compute a trivial matching answer.
C5 · NaN / infinity bypass — a graded numeric field has no NaN/Infinity rejection, so a non-finite value slips past a bare tolerance check.
C6 · Scoring contract mismatch — the reward scheme contradicts the stated grading (e.g. instruction promises partial credit but test.sh emits binary 0/1).

D · Fixtures, environment & determinism (D1–D5)
D1 · Degenerate test fixture — the initial/no-op state already satisfies the verifier, so zero real work passes.
D2 · Malformed / unparseable fixture — a shipped fixture raises a parse error under the format the solution/tests assume.
D3 · Environment build failure — an uninstallable or unpinned dependency/build step fails for the specified Python/OS/arch.
D4 · Nondeterminism in gen/solution/verification — an unseeded RNG, seed-without-default, time.time(), network fetch, or set/dict iteration changes generated data or the accepted answer across clean runs.
D5 · Unseeded build-time randomness — a key/IV/random value is generated at build/setup time without a fixed seed.

E · Anti-cheat & isolation (E1–E7)
E1 · Oracle / answers readable by the agent — solution/, tests/, a seed, or an expected value is present or importable inside the agent image during the run (e.g. COPY solution/ in the Dockerfile).
E2 · Immutable-input integrity not enforced — a protected path isn't integrity-pinned AND tampering with it changes the graded outcome.
E3 · Reward / harness plumbing exploit — a concrete agent-writable file is imported or executed as code by the verifier, letting the agent hijack the reward.
E4 · Root / elevated access exposes secrets — the agent's privileges let it read a secret/ground-truth file the verifier relies on at grade time.
E5 · Symlinked output path — the verifier reads a graded /app output path and follows an agent-created symlink to a golden/expected file.
E6 · Unsafe archive extraction — an agent-influenced archive is extracted without sanitizing member paths (absolute paths / ../ traversal).
E7 · Non-self-contained deliverable / copied oracle — the agent passes without real work by preserving/copying a retained reference tool/oracle the graded entrypoint can invoke, import, or decode.
Proven strategies to pass
These are the six things the gate actually grades on — each pairs a real defect that got flagged (red) with a real task confirmed sound (green). Several green cases were even flagged Major by a first reviewer, then confirmed sound on appeal — study the boundary carefully. Build tasks that look like the green blocks, not the red ones.

Core principle
Everything the verifier grades must be derivable by the agent from instruction.md + environment/ + shipped examples, and the verifier must independently enforce every structural requirement — not a proxy. Design backward from that.

Strategy 1 · Put every graded decision in agent-visible material
Covers: A3, A5, B3, B4 — this is the single most common cause of flags.

Enumerate every constant, threshold, tie-break, ordering, precedence, unit, and filter your verifier uses. For each, point to the exact line in instruction.md or environment/ that states or determines it. If it lives only in solution/ or tests/, document it or remove the dependency.
If a mechanism is meant to be learned rather than told, say so and ship enough data to pin it uniquely.

The runbook says dominant pairs link — but the oracle secretly also requires a 4.5 score floor. Pair P00245 is dominant under the written rule yet graded "separate." The deciding rule exists only in the solution.

Strategy 2 · Make the verifier enforce structure, not just an aggregate
Covers: C1, C2.

List every structural requirement (exact count, shape, keys, ordering, byte-exactness) and add an assertion pinning each. Never let a single aggregate (ARI, correlation, RMSE, a count tolerance) stand in for a structural constraint.
Actively try to construct a wrong-shape or degenerate answer that clears your metric. If you can, so can the agent — tighten until only real work passes.

Strategy 3 · Protect ground truth in code, not by convention
Covers: C4, E1, E2, E5.

Grade from the verifier's own /tests copy or recompute truth from inputs the agent cannot write. Never re-read an agent-writable path to derive the expected answer.
Open graded output paths with a symlink guard (O_NOFOLLOW), hash-pin protected inputs, and never COPY solution/ or tests/ into the agent image. Assume the golden path is guessable.

Strategy 4 · Make the whole pipeline deterministic
Covers: A1, D3, D4, D5.

Seed every RNG on every graded generation path with a fixed constant (a seed read from the environment without a default counts as nondeterministic). Avoid time.time(), network fetches, and digesting set/dict iteration order.
Pin dependencies exactly; never hash-match a binary built by an unversioned, mutable toolchain. Confirm the reference solution scores full reward against the verifier exactly as shipped.

Strategy 5 · Ship a complete reference that derives its own answer
Covers: A2, A4, B5.

The reference must perform every action the instruction requires (not just report), and must derive its answer from agent-visible inputs — not import a private module that hands it the crux, and not rely on a rule family the disclosed data doesn't pin.
If a private helper module is unavoidable, make sure everything it supplies is recoverable from the shipped corpus — and that the graded inputs stay inside the range the examples demonstrate.
