## WHAT MAKES BUGS HARD (models can't find these)
- Ordering/sequencing bugs (loss before principal, dedup before transform)
- Stateful interaction bugs (state propagation across retries, cache invalidation)
- Domain convention bugs (upsert vs update, SCD temporal routing, palindromic masking)
- Boundary condition bugs (<= vs < at exact timestamp match)
- Registration order vs alphabetical (invisible when both give same result)

## WHAT MAKES BUGS EASY (models find these instantly)
- int() vs round() (too well-known)
- Unused parameter (obvious code smell)
- Docstring contradicts code (trivial diff)
- First-match vs last-match (textbook)
- Longest-prefix matching (textbook networking)
- Null handling with .get() (common Python gotcha)
- Any standard CS algorithm bug (cycle detection, sorting, etc)

## DATA SCIENCE / STATISTICAL ANALYSIS — PROVEN PATTERNS (July 2026)

### WHAT WORKS (0/7 self-play every time):
1. **Domain convention bugs** — not code patterns, not textbook formulas
2. **Small-n masking** — bugs invisible with n=50, devastating with n=5-8
3. **Comparison count masking** — 1 comparison masks multi-comparison bugs
4. **Weight uniformity masking** — equal weights mask wrong-weight bugs
5. **Heterogeneity masking** — homogeneous data masks variance estimator bugs

### ACCEPTED PIPELINES:
| Pipeline | Bugs | Why 0/7 |
|----------|------|---------|
| Biostatistics (t-tests, Holm, Cohen's d) | n vs n-1 percentile, Holm sort, Bessel's correction | Convention differences invisible on visible data |
| Survival (KM, log-rank, Cox) | Censoring-before-event, n³ vs n²(n-1) variance, Breslow batching | Tied-event handling only matters with ties |
| Meta-analysis (DerSimonian-Laird, Egger, prediction intervals) | C formula parenthesization, WLS weights inverted, t df off-by-one | Uniform weights + large k mask everything |

### BUG DESIGN PRINCIPLES FOR STATS PIPELINES:
1. **Never use docstring-contradicts-code** — models catch this instantly
2. **Never use well-known formulas** (atol+rtol*|y|, 1/(p+1) exponent) — models memorize these
3. **Always hide bugs in helper functions** with plausible docstrings matching buggy code
4. **Make the bug look like a valid alternative** — not an error, just a different convention
5. **Compound bugs across modules** — fixing any 2 of 3 still fails
6. **Visible data should make the bug MATHEMATICALLY EQUIVALENT** — not just "close"

### VISIBLE DATA MASKING STRATEGIES:
- **Uniform weights** → any weight formula gives same result
- **Single comparison** → multi-comparison correction is identity
- **Large n** → n, n-1, n-2 differences vanish
- **Symmetric distributions** → ordering doesn't matter
- **Q < df** → tau² = 0 regardless of estimation method
- **Equal SEs** → WLS = OLS (wrong weights don't matter)

### HIDDEN DATA TRIGGERING STRATEGIES:
- **Small n (5-8)** → Bessel's, df differences amplified
- **Multiple comparisons (3+)** → correction methods diverge
- **Heterogeneous SEs** → weight formula matters enormously
- **Asymmetric data** → ordering/convention bugs surface
- **Q >> df** → heterogeneity estimator formula fully exercised

### WHAT FAILS (models solve these — DON'T USE):
- ODE solver internals (RK45 error scaling, step exponents) — 5-7/7 solve
- Inverted boolean comparisons (< vs >) — trivial to spot
- Well-documented algorithms (KM formula, standard error scaling)
- Any bug that a model can fix by "knowing the right formula from scipy docs"

## META-ANALYSIS TASK — KEY FINDINGS (July 3, 2026)

### What Worked (0/7 self-play):
- **Data-flow bug across modules** — the killer. Passing overall tau² to subgroups instead of re-estimating per-subgroup. Models review functions individually and miss cross-module value propagation.
- **Misleading code comment** — "common heterogeneity assumption" made the bug look intentional. ALL 7 agents accepted it as a design choice.
- **Helper function with plausible docstring** — _compute_egger_weights hides the wrong formula behind a reasonable-sounding explanation about "precision proportional to variance contribution."

### What Models Found (7/7 found these):
- Egger weights (normalized precision vs 1/SE²) — found by all because inverse-variance weighting is textbook
- Prediction interval df (k-1 vs k-2) — found by all because the function is self-contained and models know Higgins 2009

### Key Design Decisions:
1. **tau²=0 on visible data** — this is what makes Bug (c) invisible. When tau²=0, RE weights = FE weights regardless of which tau² you use. The bug ONLY matters when tau² > 0.
2. **Uniform SEs on visible data** — makes Egger weight bug invisible (any weight scheme gives same regression with uniform weights).
3. **Large k on visible data (k=15)** — makes df bug invisible (t(14) ≈ t(13)).
4. **Small k on hidden data (k=5)** — amplifies df difference AND makes the overall vs subgroup tau² differ more.
5. **Widely varying SEs on hidden (0.12-2.5)** — creates massive weight heterogeneity triggering all bugs.

### Proposal Gotchas:

## 5 REJECTION REASONS & HOW TO AVOID THEM (July 2026 — from official Dynamo guidance)

### THE GOLDEN RULE:
"If spelling out the deciding rule makes the task easy, the difficulty was fake."
A good task stays hard even when every rule is clearly stated — the model fails
because the problem is hard, not because it was missing information or misled.

### Reason 1: UNDISCLOSED VERIFIER CONVENTION (most common — ~50% of rejections)
- What: Verifier checks a format, ordering, tie-break, or convention that instruction.md never mentions
- Example: Verifier expects alphabetical ordering but instruction says "priority order"
- Example: Verifier expects k-2 df but instruction never pins the convention
- Fix: Write down EVERY rule the verifier checks in instruction.md or a file it references
- Test: Could a reasonable different implementation still pass? If only your exact choice passes and you never stated it, DISCLOSE IT.
- Our experience: meta-analysis (k-2 vs k-1), qffewau (priority vs alphabetical), historian (3× multiplier)

### Reason 2: CONTRADICTORY SHIPPED DATA
- What: A data file, config, or reference solution follows a different rule than the instruction states
- Example: instruction.md says "produces correct output on current manifest" but visible manifest triggers bugs
- Example: expected_output.json has wrong value that doesn't match oracle
- Fix: Make shipped data and reference solution OBEY the instruction exactly. Regenerate if they drift.
- Our experience: historian (visible == hidden manifest), a165448 (same issue), qffewau (expected_output wrong value)

### Reason 3: AMBIGUOUS SPEC
- What: A term or rule has two defensible readings; verifier silently accepts only one
- Example: "Use appropriate threshold" without specifying the exact multiplier
- Fix: Name the single canonical rule. Then check: once unambiguous, is the task STILL hard?
- Our experience: historian (GAP_SCAN_RATE_MULTIPLIER — had to document "small integer multiple" in code)

### Reason 4: DIFFICULTY COLLAPSES ONCE DEFECT REMOVED
- What: The single thing failing the model is one unstated/broken rule. Fix it and task is trivial.
- Example: Adding all 3 conventions to meta-analysis instruction → went from 0/5 to 5/5
- Fix: Build difficulty into genuine reasoning that SURVIVES full disclosure
- Test: With all rules stated plainly, would a strong engineer still struggle? If no, need a real crux.
- Our experience: meta-analysis (disclosing all 3 conventions made it trivial), sensor features (partial disclosure was safe)

### Reason 5: DECOYS WITH NO WAY OUT
- What: Task points agent at wrong answer through authoritative-looking file, while real rule is hidden
- Example: Comment says "use subnet scope" and nothing in instruction corrects it
- Fix: Misdirection allowed ONLY if the task itself can set the record straight
- Fix: instruction.md must explicitly protect decoys ("preserve X convention")
- Our experience: Our decoys work because instruction EXPLICITLY names them as preserved behaviors

### PRE-PUSH CHECKLIST (apply EVERY time):
1. Every verifier rule is stated in instruction.md or discoverable in agent-visible code
2. Visible data ≠ hidden data, and "produces correct output on current [input]" is TRUE
3. No ambiguous conventions — pin exact formulas/rules where multiple valid interpretations exist
4. Task stays hard even with all rules disclosed (difficulty from LOCATING bugs, not KNOWING conventions)
5. Decoys explicitly protected in instruction ("preserve the X and Y")
6. expected_output.json matches what oracle ACTUALLY produces
7. Read reviewer notes AFTER CI passes, address flags before submitting to platform

### WHY OUR TASKS SURVIVE THE GOLDEN RULE:
- Disclosing "use stepped for discrete" doesn't tell you WHERE in pipeline.py to fix it
- Disclosing "3× scan rate" doesn't tell you which function call is missing it
- Disclosing "preserve harmonic-mean estimator" doesn't reveal the data-flow bug
- The difficulty is in TRACING DATA FLOW across 6+ modules, not in knowing the convention
- The decoys compound this: even knowing all rules, agents must DISCRIMINATE 4 suspicious patterns


## AUTOMATED REVIEW (Gap Rubric Gate — runs AFTER pass@2, BEFORE pass@5)

### WHAT IT IS:
A deep gap-rubric review that reads instruction.md, solution/, tests/, Dockerfile, and Pass@2 agent traces.
It GATES the PR — Pass@5 does NOT run until this passes.

### WHAT IT CHECKS (~24 criteria):
- **Test coverage** — every requirement in instruction.md maps to an assertion
- **Correct expected values** — verifier's expected results are actually right (not buggy golden)
- **Fixture/tamper independence** — ground truth not read from agent-writable path without re-copy/integrity check
- **Traceability & consistency** — instruction → solution → tests all describe same task; paths/schemas don't contradict
- **Clean agent traces** — Pass@2 traces show no reward hacking (no writing reward.txt, no reading tests/ or solution/)
- **Difficulty evidence** — Pass@2 failures reflect intended crux, not timeouts or format artifacts
- **Environment/permissions, Dockerfile structuring, line endings, prompt-injection checks**

### WHAT IT POSTS (single comment on PR):
1. **Verdict** — PASS or FAIL. PASS = no blocking gap-criterion failure.
2. **Blocking Issues** — must be fixed before gate opens. Names file+line, ends with concrete fix.
3. **Advisory Notes** — optional improvements, never block. Still address them for cleaner R1/R2.
4. **Full deep-review assessment** (collapsible):
   - Requirement → assertion map (every requirement + test that checks it, holes highlighted)
   - Trajectory analysis of Pass@2 runs (trace integrity, intended crux reached?)
   - Domain-expert read (end-to-end traceability, expert concerns)
   - Gap rubric (each criterion PASS/FAIL/N/A with evidence)
   - CI escapes (flags misleading results — defects that slipped past or non-task failures)

### COMMON BLOCKING ISSUES:
- "A requirement in instruction.md has no matching assertion in tests/" → add the test
- "Verifier reads ground truth from agent-writable /app/ path" → mv to /tmp before pipeline, restore for pytest
- "expected_output.json value doesn't match oracle output" → regenerate expected output
- "instruction.md contradicts test behavior" → reconcile
- "test_waic is bug-blind (passes on unfixed pipeline)" → make test discriminate bug presence

### COMMON ADVISORY NOTES:
- "Ground truth generated by running oracle itself (circular)" → consider independent cross-validation
- "Edge case not exercised by hidden data" → add fixture or document why
- "Pass@2 runs didn't demonstrate intended difficulty" → may need harder hidden data
- "Dead utility functions never called" → remove orphaned code

### HOW TO HANDLE:
1. If Verdict = FAIL → read Blocking Issues → fix → push → re-runs automatically
2. If Verdict = PASS → Pass@5 runs automatically
3. ALWAYS read Advisory Notes — address them proactively for smoother R1/R2 review
4. Open deep-review to understand WHY something was flagged (requirement→assertion map shows gaps)

### KEY INSIGHT:
This gate catches the SAME issues human reviewers flag — fixing them here means fewer revision rounds later. The most common blocker is test coverage gaps (a field mentioned in instruction but never asserted in tests).

## MULTI-FILE BUG PLANTATION STRATEGY (MANDATORY — July 18, 2026)

### ⚠️ RULE: ALWAYS spread bugs across MULTIPLE files. NEVER put all bugs in pipeline.py only.

### WHY (proven by dynamo-44c68e5 failure + recovery):
- Bugs ONLY in pipeline.py: CI agent finds them in minutes by crafting test inputs (4/5 solved)
- Bugs SPREAD across 3 files: CI agent struggles because it assumes modules are correct (0/5 solved)
- The CI agent (Terminus-2 on Daytona) is MUCH stronger than self-play — it runs code iteratively for 1 hour
- Pipeline-only bugs are trivially findable by any agent that constructs its own test data

### THE WINNING PATTERN (dynamo-44c68e5 accepted, 0/5 CI):
| Bug | File | What | Why Hard |
|-----|------|------|----------|
| 1 | pipeline.py | Wrong dispatch (all derivations use same path) | Agent must know correct dispatch condition |
| 2 | cache_validator.py | Wrong field used inside validation function | Bug is INSIDE a trusted module — agent doesn't think to look |
| 3 | store_path_calculator.py | Correct function but wrong algorithm inside | Even calling the "right" function gives wrong answer |

### KEY INSIGHT: Module bugs exploit agent's TRUST bias
- Agents read pipeline.py thoroughly (it's the orchestrator)
- Agents SKIM modules (assume they're library code, correct by design)
- Putting a bug INSIDE a module means the agent must READ and UNDERSTAND the module's internal algorithm
- Combined with domain-specific conventions (Nix hashing, Prometheus histograms, etc.), this is devastating

### HOW TO IMPLEMENT:
1. Bug 1 in pipeline.py — the "obvious" bug that every agent will find
2. Bug 2 in a module — a function that does the wrong thing internally but has correct signature
3. Bug 3 in another module — a function that USES its parameters incorrectly (looks like it works)

### DECOYS STILL WORK (but less critical):
- Reversed base32 encoding trapped 5/7 self-play agents who removed it
- The ! separator trapped 0/7 (agents respected instruction protection)
- Decoys help but are NOT the primary difficulty source — module bugs are

### MASKING RULES (same as before):
- Visible data must NEVER trigger any of the 3 bugs (mathematical equivalence)
- Example: no fixed-output derivations → Bug 1 invisible
- Example: no compressed cache → Bug 2 invisible (FileHash == NARHash)
- Example: no self-references → Bug 3 invisible (function never called)

### INSTRUCTION.MD FOR MULTI-FILE BUGS:
- Do NOT say "bugs are in pipeline.py" (that narrows the search)
- Do NOT say "modules are correct" (that eliminates module bugs from consideration)
- Just say "has bugs that cause incorrect results on other data"
- Protect DECOYS explicitly ("preserve the X convention")
- Let agents discover bug locations themselves

### ACCEPTED TASKS USING THIS PATTERN:
| Task | Files with bugs | CI Result |

## MULTI-FILE BUG PLANTATION STRATEGY (July 2026 — from 12 accepted tasks)

### THE CORE PRINCIPLE:
Bugs should be VALUE-PASSING errors in the ORCHESTRATOR (pipeline.py), not formula errors in domain modules.
Every domain module should be individually correct. The bugs are in HOW the orchestrator calls them.

### BUG PLACEMENT HIERARCHY (proven effectiveness):

| Placement | Self-Play Result | CI Result | Why |
|-----------|-----------------|-----------|-----|
| ALL bugs in orchestrator (pipeline.py) | 0-3/7 | 0/5 | Agents review modules individually, find nothing |
| Bugs spread across modules | 5-7/7 | 3-5/5 | Agents review each module and find formula bugs |
| Bugs in helper functions with wrong formula | 7/7 | 5/5 | Models memorize correct formulas |
| Bugs in well-known algorithms | 7/7 | 5/5 | Textbook patterns in training data |

### THE 3 BUG TYPES THAT WORK:

**Type A: Wrong value passed to correct function (BEST — 0/5 every time)**
- Pipeline computes X correctly, then passes Y (a related but wrong value) to a module
- Module receives Y, processes it correctly, returns wrong answer
- Comment justifies why Y is passed: "Y provides the natural scaling because..."
- Example: passing content_f instead of content_gcd, passing lc(f) instead of gcd(lc(f),lc(g))
- Masking: On visible data, X == Y (mathematical equivalence)

**Type B: Wrong divisor/operand in pipeline computation**
- Pipeline uses primitive_part(result) instead of result for a subsequent computation
- On visible data: primitive_part == identity (content=1)
- On hidden data: primitive_part strips content, giving wrong intermediate
- Example: dividing by primitive_part(gcd) instead of full gcd for cofactors

**Type C: Wrong order of operations (proven in ETL, streaming tasks)**
- Pipeline calls step A before step B when order matters
- On visible data: A-then-B == B-then-A (single element, no duplicates, etc.)
- On hidden data: order produces different results
- Example: dedup before aggregate vs aggregate before dedup

### BUG MASKING STRATEGIES:

| Masking Condition | What It Hides | Example |
|-------------------|---------------|---------|
| Content = 1 | Any content-related value swap | content_f == content_gcd == 1 |
| Leading coeff = 1 | Gamma computation differences | gcd(1,1) = 1 = lc(f) |
| Single element/window | Ordering bugs, carry-forward | 1 window → no cross-window state |
| Primitive = full | primitive_part(x) == x when content=1 | Division by either gives same result |
| Uniform weights | Any weight formula bug | All weights equal → formula irrelevant |
| No shared factor | GCD = constant, simplifies everything | Coprime → trial division catches all errors |
| Degree 0 cofactor | Resultant uses special case, skips PRS | Constant cofactor → no PRS computation |

### DECOY DESIGN (makes agents FAIL by over-fixing):

**Purpose**: Create 2 correct-but-suspicious code patterns that agents will "fix" → breaking output.

**Decoy Properties**:
1. Must LOOK like a bug to a careful code reviewer
2. Must be defensible as correct (comment explains it)
3. Must CHANGE OUTPUT if modified → agent fails verification
4. Should target known model behaviors (wanting to "fix" well-known patterns)
5. MUST be protected in instruction.md ("preserve the X and Y")

**Proven Decoy Patterns**:
| Decoy | Why It Looks Wrong | Why It's Correct | Impact If Removed |
|-------|-------------------|------------------|-------------------|
| symmetric_mod after CRA | "Why map to symmetric range?" | Needed for sign recovery of negative coefficients | Wrong signs in GCD |
| Trial division verification + fallback | "Redundant check after CRA" | Catches CRA errors from insufficient primes | Wrong GCD accepted |
| Sort by key instead of timestamp | "Time series should sort by time" | Grouped processing needs key order | Wrong aggregation |
| Population kurtosis (/ n) | "Should be sample kurtosis (/ n-1)" | Window IS population in this context | Wrong statistics |
| periodogram / (2*pi) | "Unnecessary normalization" | Correct angular frequency density | 528% energy error |
| Temporal decay weighting | "Arbitrary position-based scaling" | Standard recency weighting | 42% score deviation |
| min-degree prime filtering | "Should use first prime's degree" | min-degree correctly identifies true GCD degree | Wrong GCD if first prime is unlucky |

### INSTRUCTION.MD DECOY PROTECTION:

Always include a sentence like:
"In particular, preserve the [decoy_1_description] (which [why_it's_needed]) and the [decoy_2_description] (which [why_it's_needed])."

This explicitly tells the agent these patterns are intentional. Agents STILL try to "fix" them ~40% of the time.

### VISIBLE DATA DESIGN:

The visible input MUST make every bug produce EXACTLY the same output as correct code.
Not "approximately equal" — MATHEMATICALLY IDENTICAL. Zero difference.

**Checklist for visible data**:
- [ ] Bug 1 value == correct value on visible data (prove mathematically)
- [ ] Bug 2 value == correct value on visible data (prove mathematically)
- [ ] Decoy 1 gives same output if "fixed" on visible data? NO — decoy must still break on visible!
  Actually: Decoys should produce DIFFERENT output if touched, even on visible data.
  This way agent "fixes" decoy → visible output changes → agent sees a difference → 
  might revert OR might think the new output is "correct" → fails on hidden.
- [ ] Pipeline runs without errors on visible data

### HIDDEN DATA DESIGN:

The hidden input MUST trigger ALL bugs simultaneously AND make decoy "fixes" produce wrong output.

**Checklist for hidden data**:
- [ ] Bug 1 produces different value than correct (quantify the difference)
- [ ] Bug 2 produces different value than correct (quantify the difference)
- [ ] Both bugs together produce wrong output on ≥3 tested fields
- [ ] If agent "fixes" only 1 of 2 bugs → still fails (compound requirement)
- [ ] If agent "fixes" a decoy → output changes → fails verification

### MODULE STRUCTURE (proven 7-module template):

```
pipeline.py (~180 lines) — ORCHESTRATOR: bugs HERE, calls all modules
                           Contains compute_*, run_pipeline, main
                           Comment-justified value-passing errors
                           
module_1.py (~150 lines) — CORRECT: core domain algorithm
module_2.py (~150 lines) — CORRECT: secondary computation  
module_3.py (~150 lines) — CORRECT: tertiary computation
module_4.py (~120 lines) — CORRECT: utility/helper functions
module_5.py (~100 lines) — CORRECT: data loading/formatting
module_6.py (~80 lines)  — CORRECT: output formatting

input_data.json — visible data (masks all bugs)
```

### SELF-PLAY vs CI DISCREPANCY (important!):

Our polynomial GCD task showed: **0/3 self-play and 0/5 CI (PASSED)**.

Why self-play results correlate well with CI:
- Self-play agents do ONE PASS of code reading → find bugs → fix → done
- CI agent ITERATES: makes changes, re-runs pipeline, observes output
- When bugs are INVISIBLE on visible data, iteration doesn't help the CI agent
- CI agent fixes a bug → re-runs → output unchanged → can't confirm fix worked

**Key insight**: If bugs produce ZERO difference on visible data, the CI agent's
iterative testing becomes useless — it can't verify whether fixes are correct.

Self-play results interpretation:
- 0/7 self-play → almost certainly passes CI
- 1-3/7 self-play → likely passes CI if bugs are invisible on visible data
- 4-5/7 self-play → risky, depends on whether CI agent can verify fixes
- 6-7/7 self-play → will definitely fail CI

- Bugs are in pipeline.py (orchestrator), all domain modules are correct
- Agents review modules one by one → find nothing wrong
- Bugs are value-passing errors justified by plausible comments
- Visible data makes bugs MATHEMATICALLY INVISIBLE (content=1, lc=1)
- Decoys (symmetric_mod, trial division, min-degree filtering) are protected in instruction
- CI agent can't verify fixes through iteration (output unchanged on visible data)



## PRE-SUBMISSION SELF-REVIEW CHECKLIST (Be Your Own Reviewer — July 19, 2026)

### PURPOSE:
Before pushing (or after CI passes but before platform submission), act as an R1/R2 reviewer
yourself. Walk through EVERY criterion below. If ANY fails, fix it before submitting.
This prevents revision rounds and maintains SQS score.

### THE REVIEWER MINDSET:
- You are NOT checking if the code works (CI already did that)
- You ARE checking if the task is FAIR, HARD, REALISTIC, and WELL-CONSTRUCTED
- A task can pass all CI checks and still be rejected by a human reviewer
- The reviewer reads proposal + repo files (instruction.md, task.toml, environment/, solution/, tests/, Dockerfile)
- The reviewer reads the pass@5 analysis comment on the PR

### CRITERION-BY-CRITERION CHECKLIST:

#### 1. Everything Gels Together
- [ ] instruction.md, solve.py, tests/, Dockerfile all describe and serve the SAME task
- [ ] Environment provides what the solution needs
- [ ] solve.sh produces exactly the artifacts the tests read
- [ ] Tests check what the instruction asks for (no more, no less)
- [ ] Paths are consistent across all files
- HOW TO CHECK: Read instruction.md → trace to solve.py → trace to test_outputs.py → trace to expected_output.json

#### 2. Genuinely Solvable
- [ ] A real solution path exists from the instruction
- [ ] solve.sh actually solves the STATED problem (not a narrower one)
- [ ] Oracle passed validation (CI confirms this)
- HOW TO CHECK: Read solve.py — does it fix exactly what instruction implies is broken?

#### 3. Genuinely Hard for an Expert
- [ ] Would a competent domain expert crack it quickly? (Should NOT)
- [ ] Difficulty is REAL REASONING, not tedium/volume/obscure recall
- [ ] Not a "kitchen sink" task (dozens of rules until model slips on one)
- HOW TO CHECK: Can you explain WHY it's hard in one sentence that's about reasoning, not volume?

#### 4. Realistic
- [ ] A real practitioner would be paid to produce these outputs
- [ ] The scenario is authentic (not a toy puzzle or gimmick)
- HOW TO CHECK: Would a job posting for this work exist?

#### 5. Novel
- [ ] Not a textbook or well-known published problem
- [ ] Not reproducible from a model's training data
- HOW TO CHECK: Could you find this exact solution on StackOverflow/Wikipedia? If yes, it's not novel.

#### 6. Not Over-Directed
- [ ] Instruction does NOT hand over the method
- [ ] Instruction does NOT mandate a specific tool/library
- [ ] Instruction does NOT walk through steps
- [ ] Grading is on WHAT is produced, not HOW
- HOW TO CHECK: Does instruction say "find and fix bugs" without telling which files/lines?

#### 7. Unambiguous (Sound-Alternative Test)
- [ ] Can you name a SPECIFIC sound expert approach that would FAIL verification?
- [ ] If YES → it's ambiguous → FIX IT (disclose the convention or widen tolerance)
- [ ] If NO → it's unambiguous → GOOD
- [ ] Arbitrary choices the agent must match ARE disclosed
- HOW TO CHECK: For each non-obvious output value, ask "could an expert reasonably produce a different value?"

#### 8. No Hidden Knowledge
- [ ] Solution does NOT rely on a constant/schema/threshold the agent was never given
- [ ] Everything needed is in instruction.md OR in agent-visible files
- [ ] No convention only knowable from tests/ or solution/
- HOW TO CHECK: Can you trace every expected_output.json value back to something the agent can see?

#### 9. No Answer Leakage
- [ ] No comments revealing the bug or fix
- [ ] No docstrings that say "this should be X instead of Y"
- [ ] No READMEs disclosing the solution
- HOW TO CHECK: Grep for words like "bug", "fix", "should be", "incorrect" in agent-visible files

#### 10. No Misleading Content
- [ ] No files the agent can read that point AWAY from the golden answer
- [ ] No red herrings that a reasonable agent would follow and fail
- [ ] Decoys are PROTECTED in instruction.md (agent is told to preserve them)
- HOW TO CHECK: Are decoys explicitly named in instruction.md's "preserve" clause?

#### 11. Tolerances Calibrated
- [ ] For numeric checks: would a genuinely correct solution from a DIFFERENT method pass?
- [ ] A wrong method does NOT accidentally pass
- [ ] If using exact match: output is deterministic (no randomness, seeds fixed)
- HOW TO CHECK: Is the computation fully deterministic? If yes, exact match is fine.

#### 12. Tests Match Instruction 1:1
- [ ] Every assertion traces to a requirement the instruction states
- [ ] Every stated requirement IS actually tested
